# 2026-08-12 처리량·지연 곡선 (pool 60, 제품 코드 기준)

> 앞선 [기준값 문서](2026-08-12_읽기경로_기준값과-후보풀-60to20.md)는 20→200 VU 램프의 **통합** 통계였다.
> 그걸로는 "몇 VU 부터 꺾이는가"를 알 수 없어서, 고정 VU 로 계단을 하나씩 따로 쟀다.
>
> **결론 한 줄** — 처리량 상한은 **CPU** 다. 커넥션 대기는 그 상한의 **증상**이지 원인이 아니다.
> 그래서 풀 증설은 답이 아니고, **요청당 일을 줄이는 것**만이 답이다.

## 방법

| 항목 | 값 |
|---|---|
| 코드 | `bambi-service-api` `1503964` + VM 전용 패치(actuator, pool 60 유지) |
| 부하 | 고정 VU, **워밍업 30초 별도 실행 후 버리고** 측정 2분 (`run-step.sh`) |
| 지표 | k6 `--summary-trend-stats` 에 p(99) 포함 |

| 생성기 감시 | k6 VM 자체 CPU 표본화 (`observe-k6.sh`) — **전 구간 6~9%, 포화 없음** |

생성기가 놀고 있었으므로 아래 수치는 **타깃의 한계**가 맞다.

## 읽는 법

### ① 처리량 상한은 CPU 다 — 5 VU 에서 이미 포화

동시 사용자 **5명**에서 CPU 가 이미 381%/400% 다. 그 뒤 40배를 늘려도 CPU 는 그대로고
처리량도 그대로다(오히려 12% 감소 — 경합 오버헤드).

> **최대 처리량: 게스트 ~204 RPS · 인증 ~142 RPS** (4 vCPU 축소 스택 기준)

### ② 커넥션 대기는 원인이 아니라 증상이다

10 VU 까지는 **아무도 커넥션을 기다리지 않는다**(풀 10 ≥ 동시 요청 10).
20 VU 부터 줄이 서기 시작하고, 200 VU 에서는 200 개 중 **190 개가 대기 중**이다.

200 VU 에서 응답시간 1.07초 중 **1.056초(99%)가 커넥션 대기**다.
실제 일하는 시간은 5 VU 의 p50 인 **22ms(게스트) / 40ms(인증)** 이 전부다.

**하지만 이 대기는 풀이 좁아서가 아니라 CPU 가 그 이상 못 처리해서 생긴다.**
서비스 속도가 CPU 로 고정된 상태에서 도착률만 올리면, 대기줄은 어딘가에 반드시 생긴다.
지금은 그 줄이 커넥션 풀 앞에 서 있을 뿐이다.

### ③ 그래서 풀 증설은 여전히 오답이다

README 4항 판정표의 경고가 맞았다. 풀을 20 으로 늘리면 대기줄이 커넥션 풀에서
**CPU 런큐로 옮겨갈 뿐** 처리량은 안 오르고, 동시 실행이 늘어 경합만 는다.
지금 풀 10 은 사실상 **동시성 제한기(admission control)** 로 기능하고 있다.

### ④ 답은 요청당 CPU 일을 줄이는 것

이미 검증했다 — 후보 풀 60→20 으로 요청당 일을 1/3 로 줄이자
게스트 +62%, 인증 +22% 처리량이 늘었다(1회 실험).
CPU 가 병목이라는 진단과 개선 방향이 정확히 일치한다.

## 이전 문서 정정

`hikaricp.connections.acquire` 를 실제로 재게 되면서, 앞 문서에서
**근거 부족으로 철회했던 "요청이 커넥션을 기다린다"가 실측으로 되살아났다.**
다만 인과는 반대로 잡아야 한다 — 기다림이 느림의 **원인**이 아니라 **결과**다.

참고로 acquire 지표를 못 읽던 것은 actuator 미탑재가 아니라
**관찰 스크립트의 파싱 코드 버그**였다(python f-string 안에 escape 한 따옴표 → SyntaxError).
계측이 침묵하면 대상이 아니라 계측기를 먼저 의심할 것.
