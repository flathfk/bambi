## 병목 ① — 4 vCPU 가 다 찼다

부하 중 CPU (게스트·인증 모두 동일한 그림):

```
nginx      약   8~10%
backend    약 164~186%
postgres   약 198~219%
──────────────────────────
합계       약 388% / 400%    ← 포화
```

메모리는 무관하다(backend 720 MiB, postgres 67 MiB / 15.6 GiB).

README 4항 판정표의 **"DB CPU 포화"** 칸. 같은 표가 말하듯 **커넥션을 늘리면 더 느려진다.**

## 병목 ② — 커넥션 10개가 *일을 안 하면서* 점유되어 있다

부하 중 `pg_stat_activity` (인증 표본 25개 / 게스트 표본 32개 **전 구간**):

```
백엔드 커넥션 수    = 10   ← 57개 표본 전부. 한 순간도 안 쉬고 풀 최대치
  idle in transaction : 6~8 (최빈 8)   ← 트랜잭션만 열어둔 채 쿼리를 안 함
  active              : 1~5            ← 실제로 SQL 을 도는 것
```

**게스트와 인증이 같은 패턴이다.** 개인화 때문이 아니라 `publicFeed()` 공통 구조다.

**관측 사실은 여기까지다** — 부하 구간 57개 표본 전부에서 커넥션 수가 풀 최대치(10)에
붙어 있고, 그중 다수가 쿼리를 돌지 않는 상태였다.

> ~~리틀의 법칙으로 교차검증된다 — 155.8 RPS × 64ms = 10.0~~
> **취소(2026-08-12).** 64ms 는 독립 측정값이 아니라 `10 ÷ 155.8` 로 역산한 값이라,
> 이걸로 다시 10 을 유도한 것은 순환논증이었다. 커넥션 점유 시간은 미측정이다.
> 요청이 커넥션을 **얼마나 기다렸는지**는 `hikaricp.connections.acquire`·`.pending`
> 없이는 말할 수 없다(아래 "완료로 닫으려면" ①).

### 원인은 트랜잭션 범위

`spring.jpa.open-in-view: false` 이므로 OSIV 가 아니다(application.yml:19).
`FeedService.publicFeed()` 가 **메서드 전체**를 `@Transactional(readOnly = true)` 로 감싼다
(FeedService.java:135–204). 그 안에서 하는 일:

| 구간 | 내용 | 커넥션 필요? |
|---|---|---|
| 쿼리 6개 | 후보 60건 + 좋아요수 + 좋아요 IN + 스크랩 IN + 작성자 IN + 관심사·taxonomy | ✅ |
| DTO 매핑 | 60건 `PublicCardResponse.from(...)` | ❌ |
| `rankForViewer` | 60건 점수 계산·정렬 후 20건으로 자름 | ❌ |

아래 두 구간이 커넥션을 쥔 채 CPU 만 쓴다. 그래서 풀 10 중 7~9 가 `idle in transaction` 이다.

## 개인화 비용

관찰까지 붙은 run3 끼리 비교(게스트 198.8 vs 인증 155.8):

| | 변화 |
|---|---|
| RPS | 198.8 → 155.8 (**-22%**) |
| p50 | 374ms → 464ms (**+24%**) |
| p95 | 964ms → 1.25s (**+30%**) |
| 요청당 응답 크기 | 14.1 KB → 14.1 KB (**동일**) |
| DB `active` 비중 | 상대적으로 높음(3~5) | 낮음(1~3) |

**응답 크기가 같다.** 개인화는 페이로드를 키우지 않고 서버 시간만 먹는다 —
직렬화·네트워크는 원인이 아니다. 인증 쪽 `active` 가 더 낮은 것도 같은 방향이다:
커넥션을 쥔 시간 중 실제 쿼리 비중이 줄고 애플리케이션 작업 비중이 늘었다.

## 변경 ① — `RANKING_POOL_SIZE` 60 → 20 (실제로 재보았다)

README 5항대로 **한 번에 하나만** 바꿨다. 타깃 VM 위에서만 패치·재빌드했고
레포에는 커밋하지 않았다(머지 프리즈).

`FeedService.java:89` 의 상수 한 줄. 화면 개수는 그대로 20건이다.

**응답 동일성은 증명되지 않았다.** 변경 전후 모두 게스트 피드가 20건 / 13,660 bytes 로
같은 크기였지만, 이건 `observe.sh` 가 **게스트 URL 만** 1회 호출해 바이트 수를 센 것이다.

- 인증 경로 응답은 아예 재보지 않았다.
- 해시·본문 비교가 없어 **크기가 같다고 내용이 같다는 근거가 못 된다.**
- 애초에 후보 풀을 좁히면 랭킹 대상 집합이 달라지므로 **반환 카드가 바뀌는 것이 정상**이다.
  "동일함"을 기대할 게 아니라 **얼마나 달라지는지가 곧 품질 비용**이다(아래 참고).

지금 말할 수 있는 것은 "응답 **건수**와 스키마는 그대로(20건)" 까지다.

| 게스트 | 60 | 198.8 | 374ms | 889ms | 964ms | 3.08s | 0% |

⚠️ **각 조건 1회 측정이다.** "효과를 확인했다"가 아니라 **"1회 실험에서 관찰됐다"** 가
정확한 표현이다. 변경 전 게스트는 3회 재현했지만 변경 후는 게스트·인증 각 1회뿐이다.

지연이 급증했는지는 이 숫자로 알 수 없다. p99 도 없다(k6 기본 요약에 미포함).

### CPU 가 어떻게 움직였나 (왜 늘었는지의 근거)

부하 구간 표본만 평균낸 값:

| | backend | postgres | nginx | 합 / 400% |
|---|---|---|---|---|
| 인증 60 | 179% | 197% | 10% | 386% |
| 인증 20 | 220% | **157%** | 10% | 387% |
| 게스트 60 | 163% | 215% | 9% | 387% |
| 게스트 20 | 160% | **162%** | 55% | 377% |

네 런 모두 **여전히 포화**다(377~387% / 400%). 바뀐 것은 배분이다.
Postgres 가 하던 일이 40~53%p 줄고, 그 여유가 더 많은 요청을 처리하는 데 쓰였다.
게스트 쪽 nginx 가 9% → 55% 로 오른 것은 트래픽이 62% 늘어난 결과다.

즉 **일을 줄인 만큼 처리량이 늘었다.** CPU 포화라는 진단과 결과가 일치한다.

### 대가 — 공짜가 아니다

`FeedService.java:139-142` 주석이 이 변경의 반대편을 이미 적어두었다:

> 최신 20건만 읽어 그 안에서 정렬하면, 조금 오래됐지만 내 관심사에 딱 맞는 카드는
> 애초에 후보에 못 들어와 영영 안 보인다.

후보를 20건으로 줄이면 랭킹은 사실상 "최신 20건 안에서의 재정렬"이 된다.
**처리량 +22~62% ↔ 랭킹 품질**의 거래이고, 어느 쪽을 택할지는 제품 판단이다.
이 문서가 하는 일은 그 가격표를 숫자로 만든 것까지다.

중간값(예: 40)이나 "후보는 넓게 읽되 매핑은 상위 20건만" 같은 절충안은 아직 안 재봤다.

### 바뀌지 않은 것

`idle in transaction` 7~9 / 커넥션 10 고정은 **변경 후에도 그대로**다.
후보 수를 줄여도 트랜잭션 범위 문제는 남는다 — 별개 과제다.

## 남은 개선 후보

1. **트랜잭션 범위 축소** — 근거는 `idle in transaction` 7~9/10 으로 확실하다.
   다만 **한 줄짜리가 아니다.** `PublicCardResponse.from()` 이 `card.getSources()`·
   `card.getInterestTags()` 등 지연 로딩 컬렉션을 건드려서(PublicCardResponse.java:58,66),
   `@Transactional` 만 떼면 `LazyInitializationException` 이 난다. 매핑 구간은 순수 CPU 가
   아니라 SQL 도 같이 돈다는 뜻이다. 컬렉션을 먼저 명시적으로 채우는 설계가 필요하다.
   (세 컬렉션 모두 `@BatchSize(100)` 이 붙어 있어 N+1 은 없다 — 이미 조치된 부분.)
2. **게스트 피드 응답 캐시** — 게스트는 뷰어별 차이가 없어 공유 캐시가 성립하는 유일한 경로다.
   CPU 포화가 병목이므로 일 자체를 없애는 이 방향이 가장 크다.
3. ~~커넥션 풀 증설~~ — **하지 말 것.** 풀이 꽉 찬 것은 사실이지만 원인은 부족이 아니라
   **점유 시간**이고, CPU 는 이미 포화라 늘리면 경합만 는다.

## 한계 (인용할 때 반드시 함께 말할 것)

- **"운영에서 N RPS 를 처리한다"로 쓸 수 없다.** 타깃은 nginx·backend·postgres 3개만 띄운
  축소 스택이다. 운영은 같은 4 vCPU 에 agent-api·워커 6개·MCP·웹까지 함께 있다.
- 응답은 20건 고정(13,660 bytes)이다. 피드 크기가 커지면 달라진다.
- 200 VU 에서 **에러 0%**. 여기서 잰 것은 "한계"가 아니라 **포화 구간의 지연**이다.
- `hikaricp.connections.pending` 은 못 읽었다(이 스택의 actuator 가 인증에 막힘 → 401/500).
  DB 쪽 커넥션 계수로 대체했다. 대기 큐의 길이 자체는 미측정.

## 타깃 VM 의 현재 상태 (다음 사람이 볼 것)

상태로 남아 있다.** origin/main 과 다르다. 다음 측정을 기준값부터 다시 하려면:
