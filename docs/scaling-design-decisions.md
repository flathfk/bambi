# 확장성 설계 판단 — 왜 안 썼고, 언제 쓰고, 100만 명이면 어떻게 하나

> 심사 예상 질문 대비 문서. **기술 선택의 근거를 숫자로 남긴다.**
> 작성 2026-08-10. 근거는 전부 실측이거나 코드·설정 인용이다.
> **전제: LLM 비용은 구독료로 충당한다.** 이 문서는 처리량·지연 문제만 다룬다.

---

## 0. 한 줄 요약

**확장을 고려했기 때문에 지금 안 넣었다.** 확장 가능한 *구조*(DB 큐 + lease + 수평 확장)는 처음부터 넣었고, Kafka·Redis 같은 *컴포넌트*는 필요해지는 시점을 계산해 미뤘다.

증거: **2026-08-10 리포트 워커를 1개 → 3개로 늘렸다. 애플리케이션 코드는 한 줄도 안 고쳤다**(compose `deploy.replicas` 두 줄).

그리고 **인프라를 늘리기 전에 코드에서 풀 수 있는 게 아직 남아 있다**(5장).

---

## 1. 지금 무엇을 쓰고 있나

| 원래 Kafka/Redis로 하는 일 | 우리 방식 | 근거 |
|---|---|---|
| 작업 큐 | PostgreSQL 테이블 (`agent.agent_jobs`) | — |
| 중복 처리 방지 | `FOR UPDATE SKIP LOCKED` + lease | `postgres_publish_snapshots.py` claim CTE |
| 재시도 | `attempt_count < max_attempts` + 지수 백오프 | `jobs.py` |
| 이벤트 전달 | 폴링 (service가 15초마다 claim) | `PublishPollingWorker` |
| 분산 락 | `pg_advisory_xact_lock` | `wiki_reset.py` (agent가 이미 사용) |
| 캐시 | 없음 | 필요 없음 (3장) |

배포 컨테이너 14개. Kafka·Redis·RabbitMQ·NATS **0개**. 의존성에도 없다(`build.gradle`·`requirements.txt` 모두 0건).

---

## 2. 왜 Kafka를 안 썼나 — 효과가 없어서

### 도입 비용
설치는 한 시간이면 된다. 어려운 건 그 다음이다 — 중복 소비 처리(`event_inbox`), 오프셋·리밸런싱, dead letter, 순서 보장, 운영. 세 레포 + 인프라를 동시에 바꿔야 하고 **기존 폴링은 복구 경로로 남겨야 하므로** 경로 2개를 동시에 유지·테스트해야 한다.

### 얻는 것 — 계산해봤다

```
지금      [ 생성 96초 ][ 폴링 대기 ≤15초 ]  ≈ 111초
Kafka 후  [ 생성 96초 ][ 즉시 ]            ≈ 96초
```

**13% 단축, 사용자는 체감하지 못한다.** 큐가 막힌 게 아니라 생성이 병목이기 때문이다. 컴포넌트 2개를 추가할 이득이 아니었다.

---

## 3. 왜 Redis를 안 썼나 — 쉬운데 쓸 데가 없어서

Kafka와 이유가 다르다. Redis는 컨테이너 3줄이면 붙는다.

| Redis 용도 | 현재 상황 |
|---|---|
| 캐시 | 사용자 17명. **캐시할 트래픽이 없다** |
| 분산 락 | 백엔드 **1대**. 락 걸 상대가 없다 |
| Rate limit | 온디맨드는 멱등키 `ondemand-{userId}-{type}-{분}`가 1분 1건으로 이미 막는다 |
| 세션 저장소 | JWT stateless라 세션이 없다 |

### 규모와 무관하게 남은 문제 하나
**stateless JWT의 토큰 무효화.** 비밀번호를 바꿔도 기존 토큰이 만료(120분)까지 유효하다(service-web #60 실측). Redis 블랙리스트보다 **`users.token_version` 컬럼 1개**가 더 적합하다고 판단해 후속 과제로 뒀다.

---

## 4. 깨지는 순서 — Kafka는 5번째다

| 순서 | 병목 | 성격 |
|---|---|---|
| ① | **워커 동시성 부재** | 코드 |
| ② | **LLM API rate limit** | 외부 한도 |
| ③ | **DB 커넥션** | 설정 → 인프라 |
| ④ | **스케줄러 순회** | 코드 |
| ⑤ | **큐 처리량 (Kafka)** | 인프라 |

③은 **2026-08-10에 실제로 만났다.** 워커를 3개로 늘리며 계산하니 프로세스당 최대 16 커넥션 × 상주 8개 = 이론상 128인데 PostgreSQL 기본값이 100이었다. **터지기 전에 200으로 올렸다.**

### Kafka 전에 `LISTEN/NOTIFY`
PostgreSQL `LISTEN/NOTIFY`로 이벤트의 이점(즉시 반응)을 **인프라 추가 0개**로 얻을 수 있다. agent가 outbox INSERT 시 `NOTIFY`, service가 `LISTEN`하다 깨어나 claim. 폴링은 복구 경로로 유지.

## 5. 사용자 100만 명 — 처리량으로 푼다

### 5.1 기준 숫자

실측: **리포트 1건 = 96초**(2026-08-06, 17명 27분 = 사용자당 95초). LLM 호출 10~20회.

```
100만 명 · 1일 1회 아침 브리핑

24시간에 균등 분산 → 초당 11.6건 시작 → 동시 진행 job = 11.6 × 96 ≈ 1,111개
07:00 한 시간에 집중 → 초당 278건 시작 → 동시 진행 job ≈ 26,667개
```

### 5.2 🔑 1순위 — 워커 동시성. 인프라가 아니라 코드다

```python
# workers/runtime/features/concurrency.py
async def wc_013(items, processor):
    """[WC-013] Concurrency 제어. 작업 유형별 동시 실행 수를 제한한다."""
    results = []
    for item in items:
        results.append(await processor(item))   # ← 순차
    return results
```

**이름은 "Concurrency 제어"인데 실제는 순차 `for` 루프다.** `asyncio.gather`가 없다.

리포트 생성 96초 중 대부분은 **LLM 응답 대기(I/O)** 다. CPU는 거의 논다. 그런데 **워커 프로세스 하나가 96초 동안 job 하나만 붙잡고 대기한다.**

| | 필요한 워커 프로세스 |
|---|---|
| 지금 (순차) · 24h 분산 | **1,111개** |
| 동시성 50 · 24h 분산 | **23개** |
| 동시성 100 · 24h 분산 | **12개** |
| 동시성 50 · 1시간 집중 | 534개 |

**컨테이너를 2만 개 띄우는 문제가 아니라 `asyncio.gather` 문제다.** 오늘 워커를 1→3으로 늘린 게 3배였다면 이건 50배다.

제약: 동시성을 올리면 프로세스당 DB 커넥션 요구가 커진다. `psycopg_pool`(현재 `max_size=4` × 4풀) 재조정 또는 PgBouncer가 함께 간다.

### 5.3 2순위 — 발송 시간 분산

07:00 일괄을 사용자별 시간대로 흩으면 **피크가 24배 낮아진다.** 처리량뿐 아니라 **LLM rate limit 때문에도 필수**다(아래).

**이미 계약에 있다.** 송우 가이드 §3.4가 *"사용자 지정 시간 스케줄은 service 책임"*으로 정의해뒀고, 지금은 07:00 고정만 구현한 상태다. **설계는 확장을 전제로 돼 있고 구현만 단순화했다.**

5.2와 곱하면 **26,667 → 23개**. 인프라를 뜯기 전에 코드 두 군데로 대부분이 해결된다.

### 5.4 3순위 — LLM API rate limit (진짜 외부 벽)

동시성을 올리면 다음이 막힌다. RPM보다 **TPM(분당 토큰)**이 먼저 걸린다 — 리포트는 컨텍스트가 길다.

| 방식 | 초당 LLM 호출 |
|---|---|
| 24시간 분산 | 11.6 × 15 ≈ **174/초** (약 10,400 RPM) |
| 1시간 집중 | 278 × 15 ≈ **4,170/초** (약 250,000 RPM) |

**1시간 집중은 어떤 티어로도 불가능하다.** 발송 분산이 여기서도 답이다.

**자리는 이미 코드에 있다.**

```python
async def wc_014(request):
    """[WC-014] 외부 API Rate Limit. 외부 Source와 Provider의 호출 제한을 준수한다."""
    raise NotImplementedError
```

구현 방향: ①API 키 풀 분산 ②토큰 예산 기반 스로틀링(요청 수가 아니라 토큰으로) ③provider 다중화 ④429 지수 백오프(Job 재시도 인프라가 이미 있다).

### 5.5 4순위 — DB

| 대상 | 100만 명이면 | 조치 |
|---|---|---|
| `cards` | 100만/일 = **3.65억/년** | 월별 **파티셔닝** |
| `publish_snapshots` | 같은 양 | 파티셔닝 + 오래된 것 아카이빙 |
| 벡터(위키) | 사용자당 수십~수백 문서 → **1억+ 벡터** | pgvector 단일 인스턴스 한계 → 샤딩 또는 전용 벡터 DB |
| 커넥션 | 동시성 상향분까지 | **PgBouncer** |
| 읽기 | 피드·카드 조회 | **읽기 복제본** + Redis 캐시 |

쓰기 자체는 부담이 아니다 — 초당 12 insert 수준이다. **문제는 누적량이지 순간 부하가 아니다.**

### 5.6 5순위 — Kafka

발송을 분산하면 피크가 24배 낮아지므로 PostgreSQL 큐로 상당 구간을 간다. 그래도 남는 피크를 흡수할 때 Kafka를 넣는다. **파티션 키 = `userId`** 로 잡으면 사용자별 순서도 보장된다.

### 5.7 이 구조에서 이미 잘 돼 있는 것

- **수집이 사용자 수에 비례하지 않는다** — `global_source_documents`가 전역 공유다. 기사를 사용자마다 따로 모으지 않아 **O(관심사)** 로 동작한다. 100만 명이 와도 수집량은 관심사 종류에만 비례한다
- **DB 물리 분리** — `service-db`(트랜잭션) / `agent-db`(벡터 검색). 각각 독립 스케일 가능
- **워커가 무상태** — lease 기반. 몇 개든 늘릴 수 있고 실제로 늘려봤다
- **워커 증설이 LLM 호출량을 안 늘린다** — 같은 일을 나눠 할 뿐

## 6. 아직 안 된 것 (솔직하게)

- **`wc_013` 동시성 미구현** — 이름만 Concurrency, 실제는 순차 루프
- **`wc_014` rate limit 미구현** — `NotImplementedError`
- **스케줄러 샤딩** — 전 사용자 반복문
- **백엔드 다중화 시 `@Scheduled` 중복 발화** — 멱등키로 피해는 막았지만 락은 없다
- **Blue-Green 배포** — 단일 VM, 배포 중 짧은 다운타임
- **토큰 무효화** — `token_version` 컬럼 미구현

## 7. 예상 질문·답변

**Q. 사용자 많아지는 건 생각 안 하고 설계하셨나요?**

> 오히려 확장을 고려했기 때문에 지금 안 넣었습니다. 확장 가능한 구조는 처음부터 넣었습니다 — 작업 큐를 `FOR UPDATE SKIP LOCKED` + lease로 만들어 워커를 늘려도 중복 처리가 안 나게 했고요. **오늘 실제로 리포트 워커를 1개에서 3개로 늘렸는데 애플리케이션 코드를 한 줄도 안 고쳤습니다.**
>
> 반면 Kafka·Redis는 필요해지는 시점을 계산해보고 미뤘습니다. 저희 병목은 큐가 아니라 생성 시간(96초)이고, 이벤트로 줄어드는 건 폴링 대기 15초뿐이었습니다.

**Q. 100만 명이면 어떻게 하실 건가요?**

> 단순 계산으로는 워커가 2만 6천 개 필요합니다. 그런데 저희 워커는 대부분 LLM 응답을 기다리는 I/O 바운드인데 **한 프로세스가 job 하나만 붙잡는 순차 구조**입니다.
>
> 여기에 동시성을 넣으면 프로세스가 50분의 1로 줄고, 발송 시간을 분산하면 피크가 24분의 1이 됩니다. **곱하면 20여 개**로 떨어집니다. 인프라를 늘리기 전에 코드 두 군데에서 대부분이 해결됩니다.
>
> 그다음 벽은 LLM API rate limit입니다. 1시간에 집중하면 초당 4천 호출이라 어떤 티어로도 불가능하고, 24시간에 펴면 초당 174로 떨어집니다. **발송 분산이 처리량뿐 아니라 rate limit 때문에도 필수**입니다. 이건 저희 코드에 `WC-014`로 자리가 잡혀 있고 구현만 비어 있습니다.
>
> DB는 순간 부하보다 누적량이 문제라 `cards` 파티셔닝과 읽기 복제본, 벡터 분리가 필요합니다. Kafka는 그 이후에 남은 피크를 흡수하는 용도입니다.
>
> 다행히 수집 계층은 이미 사용자 수에 비례하지 않습니다. 기사를 전역 공유 테이블에 저장해서 관심사 종류에만 비례합니다.

**Q. Kafka 왜 안 쓰셨어요?**

> 이벤트 전환 설계까지 마쳤습니다. 다만 효과를 계산하니 폴링 대기 15초를 줄이는 것뿐이었고 생성이 96초라 체감 차이가 없었습니다. 다음 단계로는 Kafka보다 먼저 PostgreSQL `LISTEN/NOTIFY`를 검토했습니다 — 인프라 추가 없이 같은 효과를 냅니다.

**Q. Redis는요?**

> 도입은 간단합니다. 다만 캐시할 트래픽이 없고 백엔드가 단일 인스턴스라 분산 락도 불필요했습니다. 필요해지는 시점은 백엔드 다중화 때인데, 그때도 분산 락은 `pg_advisory_lock`으로 대체 가능합니다. agent가 위키 초기화에서 이미 그렇게 쓰고 있습니다.
