# 장애·문제 해결 기록

> 밤새비서(AlphaCatcher)를 만들면서 실제로 겪은 문제와 해결 과정. 발표·제출 자료의 근거 문서다.
> 각 항목은 **증상 → 오진 → 진짜 원인 → 조치 → 재발 방지** 순으로 적는다.
> 추측이 아니라 **로그·코드·DB로 확인한 것만** 기록한다. 오진했던 과정도 지우지 않는다 — 그게 이 문서의 핵심이다.

---

## 관통 주제: 조용한 실패(Silent Failure)

여섯 사례 중 넷이 같은 성질을 갖는다. **시스템이 죽지 않고, 에러도 없이, 그냥 잘못된 결과를 낸다.**

| 사례 | 무엇이 조용했나 |
|---|---|
| 실시간 수집 0건 | API 키가 없어도 예외 없이 해당 소스만 빠짐 |
| 배포 중단 | 배포 도구가 죽었는데 아무도 통보받지 않음 |
| 온보딩 500 | 에러를 기록하려다 실패해서 **원래 에러가 사라짐** |
| 검색 오염 | 검색은 되는데 엉뚱한 문서가 걸림 |

**교훈:** 죽는 장애보다 안 죽는 장애가 더 위험하다. 죽으면 알림이 오지만, 조용히 틀리면 **사용자가 먼저 발견한다.**
그래서 우리는 "실패하면 시끄럽게(fail loud)"를 원칙으로 잡고, 침묵하던 지점마다 신호를 심었다.

---

## 1. 리포트에 실시간 수집 근거가 0건

**증상.** 배포 서버에서 만든 리포트 11건 모두 실시간 수집 근거가 0건. 개인 위키 자료만 인용됐다.
특정 주제("고대 이집트 미라 제작")로 재현했더니 182초가 걸리고도 근거 0건 — **인터넷 검색은 나갔는데 빈손으로 돌아왔다.**

**오진.** 로그를 두 갈래로 나눠 판단하려 했다. `실시간 자료 수집 실패` 라인이면 인프라, `실시간 자료 0건 수집` 라인이면 코드 필터.
**이 구분이 이 사건에는 통하지 않았다.**

**진짜 원인.** `docker-compose.yml`에서 리포트 워커 컨테이너에 `NAVER_CLIENT_ID`/`SECRET`이 주입되지 않았다.
API 컨테이너에는 있었다. 그런데 수집 코드(`_build_default_providers`)는 **키가 없으면 예외를 던지지 않고 그 소스만 조용히 제외한다.**
그래서 Google News RSS와 GDELT만으로 검색이 나갔고, 한국어 니치 주제는 48시간 신선도 컷을 통과하는 기사가 없어 전멸했다.
로그에는 "0건 수집"만 남아 **인프라 문제가 코드 문제처럼 보였다.**

**확정 방법.** 로그 해석을 포기하고 컨테이너 환경변수를 직접 봤다.

```
docker exec <worker> printenv | grep NAVER   →  결과 없음
```

**조치.** compose의 워커 서비스에 키 2줄 배선. VM `.env`에는 값이 이미 있어 추가 설정 없이 배선만으로 해결.
이후 `openapi.naver.com` 200 OK 확인.

**재발 방지.** 필수 키가 빠지면 조용히 빠지지 말고 기동 시점에 경고를 남기도록 요청.
그리고 **"로그로 갈리지 않으면 상태를 직접 본다"** — 환경변수·컨테이너 상태가 로그보다 결정적일 때가 있다.

## 2. 생성 요청이 9분간 `queued`에 멈춤 (장애로 오진)

**증상.** 리포트 생성 요청 후 5분이 지나도 상태가 `queued`, 진행률 0. 워커가 죽은 것으로 보였다.

**진짜 원인.** 워커는 멀쩡했다. **큐가 밀려 있었을 뿐이다.**
리포트 워커 컨테이너 1개가 job을 하나씩 순차 처리하는데, 리포트 1건에 LLM 호출이 10~20회(조사 → 생성 → 품질판정 → 검토) 들어가 1~3분이 걸린다.
같은 시각 큐 상태는 완료 28 / 대기 4 / 실행 2 / 실패 3이었고, 우리 요청은 **접수 9분 뒤에 잠겼다**(`locked_by` 확인).

**구분법(중요).** `queued` + 진행률 0이 몇 분 이어져도 정상일 수 있다. 진짜 장애와 구분하려면
**다른 job이 `running` + `locked_by`를 갖고 있는지**를 본다. 있으면 큐 적체, 없으면 워커 이상.

**확장성 실측 (2026-08-06 정기 브리핑 자동 발화).**
매일 07:00 스케줄러가 활성 사용자 전원에게 생성을 건다. 그날 발화를 그대로 측정했다.

| 항목 | 실측 |
|---|---|
| 발화 | 17건 / 17명 — **0.2초 안에 전부 접수** |
| 처리 | 완료 17, 실패 0 |
| 마지막 job 완료까지 | **26분 57초** |
| 개별 대기(user 28) | 접수 후 **8분 41초** 뒤 시작 |

접수는 0.2초, 처리는 27분. **큐에 들어가는 속도와 빠지는 속도가 8,000배 차이 난다.**
활성 사용자가 42명이므로 전원이 대상이 되면 **한 시간 이상**이 걸리고, 그동안 사용자가 누르는
온디맨드 요청은 전부 그 뒤에 줄을 선다. 사용자 수에 **선형으로** 늘어나는 구조라 확장 대책 없이는 데모에서 터진다.

**증설 시 주의.** 워커는 job을 lease로 잠그고 가져가므로 복제해도 중복 처리가 나지 않는다.
워커 식별자는 `workers/main.py`가 컨테이너 hostname 기반으로 자동 생성하므로(`{hostname}-{worker}`)
replica마다 저절로 유니크하다 — 별도 설정 없이 늘리면 된다. (`WORKER_ID` 환경변수는 service-api
발행 폴링 워커의 설정이라 여기와 무관하다. 처음에 혼동했던 지점.)

**조치·대응.** 데모 중 즉시 생성 시연은 위험하다고 판단해 세 갈래를 준비했다.
① 데모 전 미리 생성해 카드를 확보 ② 워커 컨테이너 수평 증설(lease 기반이라 중복 처리가 나지 않는다)
③ 프론트가 "생성 중" 상태를 정직하게 노출(가짜 진행률을 만들지 않는다).

**교훈.** 비동기 파이프라인에서 **"멈춘 것처럼 보이는 정상"**은 흔하다. 관측 지표에 "대기 중인 이유"가 없으면 매번 오진한다.

## 3. 에러를 기록하려다 에러를 삼킴 — 503이 500으로 둔갑

**증상.** 온보딩 마지막 단계 `POST /api/interests/sync`가 약 3.1초 뒤 500. taxonomy 조회와 관심사 저장은 정상.

**진짜 원인 (두 개가 겹침).**

1. **타임아웃.** agent 호출 읽기 타임아웃이 3초 기본값인데, 새로 얹은 taxonomy 벌크 동기화(8카테고리·44토픽)가 그 시간을 넘겼다.
2. **로깅 버그.** 타임아웃을 잡은 `catch` 블록이 예외 메시지를 AI 응답 로그에 기록하려 했는데,
   그 컬럼이 **jsonb 타입**이고 예외 메시지는 평문이라 DB가 거부했다.
   그 결과 **로깅 실패 예외가 원래의 `AGENT_UNAVAILABLE`(503)을 밀어내고** 전역 핸들러까지 올라가 500이 됐다.

**부작용.** 실패가 AI 로그에 남지 않는다. 요청 row만 있고 응답 row가 없어서 관리자 화면에서 영원히 "처리 중"으로 보인다.
→ 진단할 때 상태값이 아니라 **"응답 row가 없는 요청 row"**를 찾아야 한다.

**역설적 단서.** agent가 4xx/5xx를 **응답으로** 주면 JSON 본문이라 jsonb 삽입이 성공해 정상적으로 503이 나간다.
따라서 **500이 뜬다는 것 자체가 "agent가 응답을 아예 못 줬다"는 증거**였다.

**CI가 못 잡은 이유.** 게이트웨이 테스트가 로거를 mock으로 대체했고, 타임아웃 케이스가 없었다(5xx 응답 케이스만 있었다).

**조치.** ① 타임아웃 상향 ② 평문 메시지를 JSON으로 감싸 기록 ③ 벌크 동기화를 사용자별 경로에서 분리.

**교훈.** **관측 코드가 장애를 만들면 안 된다.** 로깅·모니터링은 실패해도 본래 흐름을 덮지 않도록 격리해야 한다.

## 4. 배포 도구가 조용히 죽어 있었음

**증상.** 이미지가 GHCR에 정상 푸시됐는데 서버는 옛 버전 그대로. 새 API가 500, 프론트도 갱신되지 않았다.

**진짜 원인.** 폴링 방식 배포 도구(watchtower) 컨테이너가 죽어 있었다. **죽었다는 통보가 어디에도 없었다.**
게다가 그전에는 배포 워크플로가 헬스체크 결과와 무관하게 초록불이었다 — 500이 떠도 "배포 성공"으로 보였다.

**조치 — 푸시 기반으로 재설계.**
① 앱 레포에서 이미지 푸시가 성공하면 배포 워크플로를 **명시적으로 트리거**
② 트리거용 토큰이 없으면 **의도적으로 빨간불**(침묵 방지)
③ 배포 후 헬스체크가 200이 아니면 **exit 1**로 실패 처리
④ 배포된 이미지 다이제스트를 로그에 남겨 "무엇이 올라갔는지" 추적 가능하게
⑤ 폴링 도구 제거

**교훈.** **"아무 일도 안 일어남"이 성공처럼 보이는 파이프라인은 위험하다.** 성공은 증명돼야 하고, 실패는 시끄러워야 한다.

## 5. 검색 색인이 페이지 전체를 담아 무관한 문서가 걸림

**증상.** 검색에 엉뚱한 문서가 잡힌다. 저장된 본문에 사이트 메뉴·관련기사 목록·광고가 함께 들어 있어,
**관련기사 목록에 낀 단어 하나로** 주제와 무관한 문서가 매칭됐다.

**원인.** 본문 수집기가 페이지를 통짜로 가져오는데, 그 결과를 그대로 검색 색인 대상으로 썼다.

**조치.** 원문(`markdown`)은 **그대로 보존하고**, 검색 전용 정제본(`search_body`) 컬럼을 따로 뒀다(상한 6,000자).
새로 수집되는 문서는 자동으로 채워지고, 기존 문서는 백필 스크립트로 채웠다.
백필은 **재수집하지 않는다** — 원문이 이미 DB에 있어 읽어서 자르기만 한다(외부·LLM 호출 없음).

**결과(실측).** 941건 정제, 색인 텍스트 **19,241,262자 감소**(문서당 평균 20,447자).
전체 1,449건이 모두 채워졌고 원문 유실 0건을 별도 쿼리로 확인했다.

**설계 판단.** 원문을 덮어쓰지 않고 **파생 컬럼을 옆에 두는 방식**을 택했다. 정제 규칙이 나중에 바뀌어도 원문에서 다시 만들 수 있고,
백필 도중 멈춰도 이어서 돌릴 수 있다(아직 안 채운 것만 고른다 = 멱등).

## 6. LLM이 만든 관심사를 우리 분류 체계에 붙일 수 없음

**증상.** 관심사 화면을 대분류(테크·IT / 비즈니스·경제 / …)로 묶으려 했는데 **20건 중 20건이 "기타"로 떨어졌다.**

**시도와 실패.** 관심사 이름을 taxonomy의 주제명·키워드와 문자열 대조하는 방식을 만들었다.
완전일치 → 키워드 일치 → 부분 포함까지 3단계로 넓혔는데도 거의 맞지 않았다.
`SK하이닉스`·`삼성전자`가 "산업·기업"에 속한다는 판단은 **세상 지식**이라 문자열 비교로는 원리적으로 불가능하다.

**드러난 더 근본적인 문제.** 관심사 자체의 입도가 들쭉날쭉했다. `정다각형`·`OpenWiki`·`API 키 발급` 같은
**문서 파편이 관심사로 승격**돼 있었다. 분류를 고쳐도 이건 남는다.

**해결 방향.** 분류는 **관심사를 만드는 쪽(LLM)이 함께 부여**해야 한다.
확인해 보니 조건이 이미 갖춰져 있었다 — agent는 우리 taxonomy를 전달받아 **DB에 저장까지 하고 있었고**,
관심사 응답에 `category` 필드도 존재했다. 다만 그 값이 taxonomy ID가 아니라 자유 문자열이었다.
→ 응답에 taxonomy의 안정 ID를 채워달라고 요청했다. 받는 즉시 매칭 코드만 교체하면 되고 화면 구조는 그대로다.

**중간 조치.** ID가 오기 전까지 빈 대분류를 감춰 화면 노이즈를 줄였다(상수 하나로 되돌릴 수 있게).
같은 문제가 **홈 피드 추천**에도 있다 — 카드 태그와 사용자 관심사를 문자열 완전일치로 비교하고 있어서,
관심사가 `AI·머신러닝`인 사용자가 `피지컬 AI` 태그 카드를 못 받는다. **한 번의 계약 변경으로 두 화면이 함께 해결된다.**

**교훈.** LLM 출력을 우리 스키마에 **사후에 끼워 맞추려 하면 깨진다.** 생성 시점에 스키마를 주는 편이 정확하고 싸다.

## 부록: 진단할 때 실제로 도움이 된 것

- **로그보다 상태를 먼저 본다.** `printenv`·`docker ps`·DB 한 줄 쿼리가 로그 100줄보다 결정적일 때가 많았다.
- **재현 조건을 좁힌다.** "리포트가 이상하다"가 아니라 "이 주제로 이 시각에 넣은 job"까지 좁혀야 원인이 갈린다.
- **오진을 기록한다.** 아니었던 가설(마이그레이션 누락·DB 스키마 불일치 등)을 지우지 않아야 같은 길을 두 번 안 간다.
- **컨테이너 재생성은 로그를 지운다.** 배포가 돌면 이전 로그가 통째로 사라진다. 사고 조사는 배포 전에 해야 한다.
